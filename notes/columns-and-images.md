# 段組みと画像配置 — 設計

「文章の段落分け（横 2 段など）」と「画像がある場合の配置デザイン」の設計。
対象は v0.14〜v0.19。前提となる現在地と課題は `status-and-plan.md`。

技術事実は **pandoc-wasm 1.1.0（= pandoc 3.10）を Node から回した実測**。
実機 iPad・PowerPoint・Word・epub リーダーでの見え方は**すべて未検証**で、
その旨は個別に明記する。

三層分離（`roadmap-pptx.md`）の割り当てが本設計の主題で、
**段組みの構造は内容層、寸法はテーマ層、一回性の上書きは文書デザインデータ層**に落ち着いた。

---

## 決定事項

| 論点 | 決定 | 根拠 |
|---|---|---|
| 段組みの記法 | pandoc ネイティブの `::: {.columns}` / `::: {.column}` を**そのまま**使う。意味クラスは `{.columns .compare}` のように**波括弧の中へ重ねる** | 独自語彙にすると素の pandoc / Quarto で 2 段にならず、内容層の可搬性（.md 書き出し・Obsidian 連携）が壊れる。波括弧なしの 2 語（`::: columns compare`）は**無警告で段組みが消える**ので、UI が入れる記法は必ず波括弧つきにする（実測） |
| 列幅・段間 | **テーマ層**が持つ。reference-doc の `Two Content` レイアウト枠を書き換えて pandoc に渡す | 原稿の `width=` は pptx で完全に無視される（実測: 4 通りで slide1.xml の sha256 が一致）。一方レイアウト枠の座標は出力に効く |
| 1 枚だけ列比を変える | **文書デザインデータ層**。変換後の spTree で `<p:ph idx>` を特定して `<a:xfrm>` を注入 | 一回性の上書きは第3層の定義そのもの。装飾と同じ EMU 矩形の語彙で持てる |
| 原稿の `width=` | **UI からは挿入しない。手で書かれていても除去しない**。pptx で効かない旨を Diagnostic（情報）で伝える | 効かない値を既定で埋めるのは嘘。docx では**列については痕跡ごと消える**が、Web では `style="width:40%"` として実際に効く（実測） |
| 画像の寸法・位置 | 第一手段は**段組み**（どの列に置くか）。自由配置は**文書デザインデータ**の EMU 矩形で `<p:pic>` の `<a:xfrm>` を上書き | pptx は画像の `{width=50%}` も `{width=1in}` も無視する（実測: ext が 1 EMU も変わらない）。原稿の記法で持てる余地が無い |
| 3 列以上 | **UI から作らせない**。上限は変換器が `capabilities` として申告し、UI と Diagnostic がそれを見る | pandoc の pptx ライターの制約であってテーマの選択肢ではない。テーマに焼くと自前 writer へ替えた瞬間に古くなる |
| Comparison | **避けない**。テーマ側で枠を直すか Diagnostic で書き手へ返す | 「列の中身を正規化する Lua」は本文を無警告で削る。テーマが内容を変えるのは三層分離違反 |
| テーマの不変条件 | テーマが触ってよいのは**寸法・色・レイアウト選択**まで。**ブロックの順序には触らない** | 形式ごとに読み順が変わるなら「一つの原稿から刷り分ける」ではなくなる。※ docx の「並置を保つ」だけは表への変換を伴うので例外扱いにし、既定にはしない（後述） |
| スライド区間の不変条件 | 挿入 UI は「pandoc のスライド数 == `slideSegments` の区間数」が保たれる形しか作らない | 段組みはスライドを割る（実測）。割れると `contentIndexOf` が **文書全体の**編集を止める |
| 装飾・配置とガード | `contentIndexOf` の枚数一致ガードは**原稿へ書く操作にだけ**掛ける | 装飾・配置は原稿に書かない層。表を 1 つ入れただけで装飾が使えない現状は層の取り違え |
| 後処理の適用点 | xfrm 注入は `doConvert` と `doExport` の**両方**が通る位置に置く | 現状 `applyDecorations` は `doExport` だけを通る。配置で同じ構造にするとプレビューと出力が食い違う |
| UI の置き場 | 段組みは段落長押しの用途メニュー。画像配置は全画面の配置モード。**`DecorSheet` には足さない** | パネルはすでに過密で、軸（スライド 1 枚）が本文構造と合わない |

## 実測で確定した事実

### 1. 段組みはスライドを割る（新しい落とし穴）

`# 見出し` の下に段組みと本文をどう並べるかで枚数が変わる。**非 INFO の警告はゼロ。**

| 原稿 | pandoc | レイアウト | タイトル |
|---|---|---|---|
| 見出し + 段組みのみ | **1 枚** | Two Content | あり |
| 見出し + 導入 + 段組み | 2 枚 | Title and Content → Two Content | 1 枚目のみ |
| 見出し + 段組み + 後続 | 2 枚 | Two Content → Title and Content | 1 枚目のみ |
| 見出し + 段組み + 段組み | 2 枚 | Two Content → Two Content | 1 枚目のみ |
| 見出し + 段組み + `::: notes` | **1 枚** | Two Content | あり |

`slideSegments`（境界は行頭 `# ` と水平線。`***` のほか `---` `___` も水平線として拾う。
コードフェンスの中は無視する）の区間数は、どの行も 1。
つまり**一致するのは 1 行目と 5 行目だけ**。

**不変条件**: 段組みのブロックが、そのスライド区間の中で
（見出しと、末尾の `::: notes` を除いて）**唯一のブロックであること**。
これを外すと `contentIndexOf` が `null` を返し、ノート編集・改行編集・装飾パネルが
**文書全体で**止まる。しかも現在の Alert 文面は「表の後ろでスライドが分割されている場合など」で、
段組みが原因だと書き手には分からない。

### 2. 3 列目は無警告に近い形で消える

3 列書くと先頭 2 列だけが出力され、3 列目は消える。残る痕跡は 1 件だけ:

```json
{"type":"BlockNotRendered","verbosity":"INFO","pretty":"Not rendering Div (\"\",[\"column\"],[]) [Para [Str \"右\"]]"}
```

`verbosity` は **INFO**。しかもブリッジの `classify()` は `RULES` の正規表現 3 本と
突き合わせるだけなので、この JSON は**どれにも一致せず「その他の警告 / info」に落ちる**。
格上げには `RULES` に `BlockNotRendered` の行を足す必要がある。

### 3. 波括弧なしの 2 語は段組みにならない

```
::: columns            → Two Content（段組みになる）
::: columns compare    → Title and Content（段組みが消える・警告ゼロ）
::: {.columns .compare} → Two Content（段組みになる）
```

意味クラスを重ねるなら**波括弧が必須**。UI が挿入する記法は必ず波括弧つきにする。

### 4. 列幅は原稿では決まらない。テンプレートが決める

`width=` を 4 通り（指定なし / 40%:60% / 10%:90% / 1in:3in）試して、
**slide1.xml の sha256 が完全に一致した**。pptx は列幅を見ていない。

pandoc 既定テンプレートの `Two Content` レイアウトは
左 x=457200 / 右 x=4648200 / 各 cx=4038600（段間 152400 EMU = 12pt）を持ち、
スライド側には座標が書かれない（レイアウト継承）。
**したがって列幅の所有者はレイアウト = テーマ層**である。

なお現在の「テンプレート配線盤」（0.11.0）がするのは `<p:cSld name>` の書き換えだけで、
`<a:xfrm>` には触れない。テンプレートは文書ごとの持ち物で `.morphodesign` にも含まれないため、
**ロードマップが言う「文書間で再利用できるテーマ」はまだ存在しない**。

### 5. パーサの実バグ 3 件（段組みで露出する）

`status-and-plan.md` の A-1・A-2・A-6 と同じもの。根拠となる実測値:

```
slideMaster1   title=ctr / body idx1=(anchor なし) / dt idx2 sz="half" anchor="ctr"
Two Content    body idx1 x=457200 cx=4038600 / body idx2 x=4648200 cx=4038600（どちらも anchor なし）
Comparison     body idx1 x=457200 anchor=b / body idx3 x=4645026 anchor=b（type="body" が 2 つ）
lstStyle lvl1  master title=3300 body=2400 ／ Two Content=2100 ／ Comparison=1800
               ／ Content with Caption title=1500 body#2=1050 ／ Picture with Caption title=1500
```

- 右列の `ctr` — レイアウトに anchor が無いのでマスターへ落ち、`idx=2` の**日付枠**を拾う
- Comparison の重なり — `type` を `idx` より先に照合するため、`type="body"` が 2 つある表で先頭勝ちになる
- 字サイズ — `DeckInfo` はマスターの 1 組しか持たないので、段組みの本文が 14% 大きく、
  `Content with Caption` のタイトルは 2.2 倍で描かれる

**`sz="half"` は「列である」の印にはならない。** 列でないもの（Content with Caption の
本文枠）にも付き、列なのに付かないもの（Comparison の左見出し）もある。
列の判定は**レイアウト名（Two Content / Comparison）と `phIdx` の組**で行う。

### 6. 画像の配置は pandoc が全部決めている

400×200 と 300×900 の PNG で実測（スライドは **9144000×5143500 EMU = 10×5.625 in**・`type="screen16x9"`）。

| 原稿 | レイアウト | 枚数 | 画像の位置と大きさ |
|---|---|---|---|
| `![](横長.png)` のみ | Title and Content | 1 | (1.29, 1.31) 7.42×3.71 in |
| `![](縦長.png)` のみ | Title and Content | 1 | (4.39, 1.31) 1.24×3.71 in |
| `![キャプション](横長.png)` | Title and Content | 1 | (1.85, 1.31) 6.31×3.15 in（キャプション段落が後ろに付く） |
| 本文 → 画像 | **Content with Caption** | 1 | (3.90, 1.22) 5.58×2.79 in（本文が左・画像が右） |
| 画像 → 本文 | Title and Content ×2 | **2** | 割れる |
| 画像 ×2 | Title and Content ×2 | **2** | 割れる（2 枚目はタイトルなし） |
| 段組みの左右に画像 | Two Content | 1 | 左 (0.50, 2.06) 4.42×2.21 / 右 (5.44, 1.31) 3.71×3.71 |

読み取れる規則:

- **単独の画像は本文枠に高さ基準で収まり、水平中央に置かれる**（縦長でも高さいっぱい）
- **列の中の画像は幅基準で収まり、垂直中央に置かれる**
- **「本文の後ろに画像」だけが Content with Caption を選び、左右に並ぶ**。
  順番を逆にすると 2 枚に割れる。**画像とテキストの並置を意図して作るなら段組みが正解**
- `{width=50%}` `{width=1in}` は**すべて無視される**（ext が 1 EMU も変わらない）

### 7. 画像の照合キーは `descr` だけでは足りない

- `![](a.png "図のタイトル")` と書くと `descr="図のタイトル\n\na.png"` になる。
  ファイル名一致で照合すると外れる（プレビューの `images[].name` もこの文字列になる）
- 同じ画像を左右の列に置くと、`<p:pic>` が 2 つとも `descr="a.png"` かつ `id="0"` で**完全に同一**。
  段組みという本命のケースで一意にならない

→ 照合キーは「`descr` の最終行をファイル名として切り出す」＋「spTree 内の出現順」の組にする。

### 8. 形式ごとの落ち方

| 形式 | `::: {.columns}` の行方 |
|---|---|
| pptx | Two Content（2 列まで）。列幅は無視 |
| docx | **痕跡ゼロ**。`w:cols` 0 個・`w:tbl` 0 個・文字列 `40%` は出力に無く、左→右の順に段落が並ぶだけ。**警告ゼロ** |
| html | `<div class="columns"><div class="column" style="width:40%;">` がそのまま出る。しかも pandoc の既定 CSS が `div.columns{display: flex; gap: 1.5em;}` / `div.column{flex: auto;}` を持つので、**Web では素で 2 段になり、`width=` も効く** |

epub は既定スタイルシートに `div.column{display:inline-block; width:50%}` 相当を持つ。
`css:` オプションは **html では外部参照（`<link>`）になり WebView で 404**、
**epub では既定スタイルシートごと置換**する。どちらも困るので、テーマ CSS は
`include-in-header` で注入する（既定を保ったまま head へ入ることは実測済み）。

## 記法

```markdown
# 二つの案

::: {.columns .compare}
::: {.column}
**案 A** — pandoc をそのまま使う。

![断面図](zumen.png)
:::
::: {.column}
**案 B** — 自前 writer に差し替える。
:::
:::

::: notes
ここは発表者ノート。段組みの外でも中でも notesSlide に隔離される。
:::
```

- 構造クラス `.columns` / `.column` は**必ず書く**。素の pandoc・Quarto でそのまま 2 段になる
- 意味クラス（`.compare` / `.note-aside`）は**追加**。初期は 2 種だけにする。
  比率以外（段間・揃え・罫線）で差が出るテーマを実際に書くまで名前は増やさない
- **波括弧は必須**（実測 3）
- `width=` は UI から入れない。手で書かれた場合は残し、pptx では効かない旨を情報として出す
- 画像は素の `![](x.png)`。寸法・位置は原稿に書かない
- **段組みは見出し区間の唯一のブロックにする**（実測 1）。上のサンプルは
  画像を列の中に入れることでこれを守っている。列の外に画像を置くとスライドが割れる
- UI ラベルは「**段組み**」。Re:VIEW では `[column]` が囲み記事を指すので「カラム」は避け、
  `column` の語を将来の囲み記事のために空けておく

既存記法との衝突:

- `::: notes` は段組みの中でも外でも notesSlide に隔離される（実測）
- ルビ `{漢字|かんじ}` の Lua パターンは `|` を要求するので `{.compare}` にはマッチしない。
  そもそも属性はリーダーが構文段階で消費する
- **衝突する相手は 2 つある**。改行編集（`locateEditable` が `:::` 行を段落として飲み込む）と、
  画像挿入（カーソルが行の途中だとフェンス行を 3 行に割る）。どちらも v0.14 で塞ぐ

## 形式ごとの刷り分け

テーマは意味クラスを 1 本の Lua と形式別の資材へコンパイルする。**内容は変えない。**

### pptx

1. `.columns` はそのまま渡す。Two Content が選ばれる
2. 列比が 1:1 以外のとき、テーマは reference-doc の `Two Content` 枠を書き換えて渡す（**layout 経路**）。
   これがデッキ全体に効く既定
3. 1 枚だけの上書きは、変換後の spTree で `<p:ph idx>` を特定して `<a:xfrm>` を注入（**slide 経路**）。
   経路の選択は**コンパイラが行う**。テーマには `ratio` だけを書かせ、経路名は書かせない
4. 画像の自由配置は `<p:pic>` を「`descr` の最終行 + 出現順」で特定して off/ext を上書き。
   前面へ出す場合は spTree 内で末尾へ移す

注入先の特定は必須。段組みスライドの空 `<p:spPr />` は**タイトルを含めて 3 つ**あり、
素朴に全置換するとタイトル枠まで動く。

**テンプレート未取り込みの文書には reference-doc が存在しない**（リポジトリに .pptx は
MIT を保つため意図的に 1 つも置いていない）。既定テーマで列比を変えるには
「1 度変換して出力からレイアウトを採取 → 書き換えて再投入」となり、
ライブプレビューで変換が 2 回になる。47 ms の前提が崩れるので、
**既定テーマでは layout 経路を使わず slide 経路に寄せる**か、
出力 pptx の `slideLayout*.xml` を後処理で直接書き換える第三の経路を測る（**未検証**）。

後処理は現在 4 系統ある（配線盤の `applyAssignments` / 文字サイズの `applyTextSizes` /
装飾の `applyDecorations` / 今回の列比・画像）。**適用順を 1 箇所で決める**こと。
とくにユーザーのテンプレートで `Two Content` が配線盤で未割り当ての場合、
列比の書き換え先が存在しない — このときは slide 経路へ落とす。

### docx

既定は「**流す**」（何もしない）。段組みは消え、左→右の順に 1 本になる。
順序は保たれ警告も出ない（実測 8）。

テーマが「並置を保つ」を選んだ場合のみ、Lua が罫線なしの 1×N 表へ落とす。
pandoc 既定の Table スタイルは `tblBorders` も `tcBorders` も持たず、罫線はヘッダ行の
条件付き書式 1 本だけで、ヘッダの無い表では `w:tblLook` により無効になる（実測・検証器 0 errors）。
**未検証なのは Word 実機での見え方だけ。**

`<w:sectPr><w:cols>` による本物の蛇行段組みも技術的には通るが、**列の境界が出力に残らない**ため
プレビューが描けるものと一致しない。当面は選択肢に出さない。

これは「テーマはブロックの順序に触らない」の唯一の例外なので、**既定にはしない**。
選んだ文書でだけ効く明示のオプションとして持つ。

### epub / Web

クラスも `width=` もそのまま残り、pandoc 既定 CSS で 2 段になる（実測 8）。
テーマは CSS を生成して `include-in-header` で注入する。3 列以上もそのまま出る。
**pptx だけが 2 列に落ちる**、という劣化になる。

既存の Web プレビューは変換後の HTML へ `</head>` 直前で `WEB_CSS`
（日本語フォント + `.notes{display:none}`）を注入している。テーマ CSS を
`include-in-header` で入れると cascade 上は `WEB_CSS` が後になる。
**どちらを正とするかを決める**（テーマを勝たせるなら注入順を入れ替える）。
画像のある原稿では `embed-resources: true` が立つため、外部 CSS を参照する余地は無い。

### PDF

`to: 'pdf'` が wasm で原理的に可能かの実験自体が**未実施**。
v0.17 でこの 1 回の実験だけは消化して `preview-formats.md` の決定事項を閉じる。

## プレビューの描画

既存フィールドは変えず追加のみ。すべて後方互換。

```ts
export interface SlideShape {
  // 既存: placeholder / phIdx / frame / anchor / paragraphs
  /** <p:ph sz=""> の生値。OOXML の枠サイズ種別であって「列である」の印ではない（実測） */
  phSz?: 'half' | 'quarter' | null;
  /** レイアウト固有 lstStyle で解決した階層別字サイズ（1/100pt）。null は DeckInfo 既定 */
  szLvl?: number[] | null;
}

/** 表（p:graphicFrame）。まず枠だけ描いて「消えない」ことを保証する */
export interface SlideTable {
  x: number; y: number; w: number; h: number;
  /** 解析済みのセル。未実装のあいだは undefined */
  rows?: string[][];
}

export interface SlideOutline {
  // 既存: index / layout / shapes / images / notes
  tables: SlideTable[];
  /** spTree の文書順。shapes/images/tables の重なり順を復元する唯一の情報 */
  order?: Array<{ kind: 'shape' | 'image' | 'table'; i: number }>;
}
```

- **`szLvl` は必須**。現状レイアウト固有の `lstStyle` を読まないため、段組みの本文が 14% 大きく、
  `Content with Caption` のタイトルが 2.2 倍で描かれる（実測 5）。
  「実際の出力そのものを読む」原則への実測済みの違反であり、段組みを一般提供する前に直さないと
  **唯一の安全弁（嘘はプレビューで露見する）が働かない**
- 「この図形は列か」はレイアウト名と `phIdx` で判定する。`phSz` は補助情報として持つだけ
- **意味クラスはシーンに載せない**。クラスは pandoc が消費して出力に残らず、
  `.compare` と `.note-aside` は Lua 適用後の pptx では同一の XML になる。UI 側が原稿から引く
- `DocBlock` は当面変更しない。docx に段組みの痕跡が無い以上、文書プレビューが
  「列が消えて順に流れる」と描くのが実出力そのもの。表モードを実装したときだけ `kind:'columns'` を足す

文書デザインデータ（一回性の配置）:

```ts
export interface Placement {
  id: string;
  /** 見出しへ自動付与した {#s-xxxx}。無い区間では null で contentIndex に落ちる */
  slideKey: string | null;
  contentIndex: number;
  kind: 'columns' | 'image';
  /** columns: 列の矩形（EMU、左→右）。image: 1 個 */
  frames: Frame[];
  /** image: descr の最終行から切り出したファイル名 */
  name?: string;
  /** image: 同名が複数あるときの spTree 内の出現順（0 始まり） */
  occurrence?: number;
  front?: boolean;
}
```

**`version: 1` のまま足せるが、フィールドを増やすだけでは保存されない。**
`store/designs.ts` の `loadDesign` と `design/designFile.ts` の
`parseDesignFile` / `serializeDesign` はいずれも明示フィールドの allowlist で組み直す方式なので、
**3 箇所すべてに `placements` を足さないと無警告で消える**。装飾と同水準のサニタイザ
（ID の文字種・数値域・制御文字）も要る。

**スライド寸法が変わる場合の扱いが未決**。`Placement` を EMU 絶対で持つと、
4:3 のテンプレートに差し替えたときに配置が崩れる。装飾も同じ弱点を持つが、
装飾は「飾りがずれる」で済むのに対し、列比と画像配置は本文の見え方が壊れる。
**寸法に対する割合で持ち、EMU は解決値として扱う**方が安全（要判断）。

## UI と操作（iPad）

原稿への書き込みは `patchBody`（front matter を保って body 差し替え → epoch remount）に集約する。
**現状は画像挿入だけがこの経路を通らず**、カーソル位置へ直接 splice して front matter 保護を
自前に再実装している。配置モードに着手する前に寄せる。

- **段組みを作る**: プレビューの段落長押し → 用途メニュー（改行 / **段組みにする** / ノート）。
  すでに学習済みの入口なので新しい語彙が増えない。挿入は不変条件を守る 2 形だけ:
  - そのスライドの本文がまるごと段組みになる場合 → 見出し直下に `::: {.columns}` を作る
  - 本文の途中から作る場合 → **見出し → 既存本文 → `***` → 段組み** の順に `***` を差し込む

  どちらにも当てはまらない選択は用途メニューに出さない
- **どの列に書くか**はフェンスの中にキーボードで打つ。列の割り当てを UI に持たせない
  （原稿にフェンスがあるので、エディタペインだけを見ても構造が分かる）
- **画像を選ぶ**: プレビューの画像には現在当たり判定が無い。`DecorEditLayer` の分担
  （描画は Surface / 当たり判定は透明レイヤー）を画像へ一般化する
- **全画面の配置モード**: `SlideShow` の stage に `DecorEditLayer` を載せる。
  0.6.3 で保留された「編集専用画面を作るか」への回答をここで出す。
  ただし stage は**横ページングの `ScrollView` と幅 22% の左右タップゾーンを含む**ので、
  配置モード中は `scrollEnabled={false}` と端タップの無効化が要る
  （消えるのは縦スクロールとの競合だけ）。ピンチズームもここに入れる
- **テーマの入口**はヘッダに新設し、文字サイズ・テンプレート配線盤をそこへ移す。
  `DecorSheet` は装飾インスタンスだけにする
- **ガードの層分け**: 原稿へ書く操作（段組み挿入・改行・ノート）は `contentIndexOf` を通す。
  装飾・配置は通さない。Alert の文面に段組みを追加し、
  「段組みは単独のスライドにしてください」＋ワンタップで `***` を入れる導線を出す
- **取り消し（Undo）が無い**のは既知の弱点。`patchBody` は epoch remount で `TextInput` を
  作り直すため、ネイティブの Undo 履歴が切れる。段組み挿入は複数行の破壊的編集で、
  `***` の挿入はスライドの割り方まで変えるので、**現行のどの編集より重い**。
  `patchBody` に 1 段のスナップショットを持たせ、シートに「元に戻す」を出す（v0.15 の範囲に含める）
- **楽観ロック**を `patchBody` の共通の作法へ引き上げる。現在は改行編集にしかなく、
  シート表示中に外部ファイルが降りてくるとノート編集は黙って上書きする

**段組みの挿入 UI はスライドプレビューにしか置けない**（文書・Web プレビューには編集ジェスチャが
1 つも無い）。段組みは内容層の構造なので本来は形式に依らないが、
`headingSegments` への一般化（`preview-formats.md` の積み残し）が前提になる。v0.17 で解消する。

### プレビューと出力の一致

往復検査（注入した pptx を解析し直してシーンと突き合わせる）を `check-deck` に置く。

## 自前 writer へ差し替えたときに生き残るもの

**生き残る**: 原稿の記法（`::: columns` は AST の語彙であって pandoc の実装ではない）／
テーマの語彙（`ratio` / `gap` / `area`）／中間表現（**EMU 矩形 + `schemeClr` 参照色 + レイアウト名**）／
`Placement` と `.morphodesign`／プレビューの型と描画／
当たり判定・配置モード・長押しメニューといった UI の全部。

**作り直す**: 意味クラス → 形式別資材のコンパイラのうち Lua の部分、
reference-doc の枠書き換えと spTree 注入、pandoc の癖の回避（3 列消滅・Comparison・空 `spPr` の特定）。
自前 writer なら 3 列制約も Comparison も最初から存在せず、列比は writer が直接書く。

**記法の読み取りは丸ごと移植とはいかない。** `markdown-it-container`（MIT）で読めるのは
波括弧なし 1 語の `::: columns` まで。本設計が採る `{.columns .compare}` は pandoc の属性構文なので、
**属性パーサは自前で書く**ことになる（数十行の規模）。

**テーマに焼いてはいけないもの**: `maxColumns` は変換器の `capabilities`、
layout/slide の経路選択はコンパイラの実装詳細。共有・Git 管理されるテーマファイルに
pandoc 3.10 固有の制約を書くと、writer を替えた瞬間に全テーマが古くなる。

**ライセンス**: 組み込みテーマに reference-doc（.pptx / .docx）を同梱すると、
pandoc 既定テンプレートから起こしたものはリポジトリの MIT に抵触する
（現在リポジトリに .pptx / .docx は 1 つも無い）。**組み込みテーマはテーマファイルのみ**とする。
実行時に pandoc の出力を取り込んで書き換える layout 経路は「使用」なので GPL の義務は発動しない。

## リスクと未検証

- **PowerPoint / Word / epub リーダー実機での見え方。** とくに `<a:xfrm>` を注入した pptx が開けるか。
  検証器が 0 errors でも落とし穴 9（検証器は通すが PowerPoint は拒む）の前例がある。
  v0.18 の受け入れ条件に実機開封を置く
- **後処理を挟んだ端から端までの遅延。** 47 ms は pandoc のみの値で、装飾注入を含む後処理は
  0.13.0 時点でも一度も測られていない。v0.18 で hot path に乗るので、その前に内訳を出す
- **既定テーマでの列比。** reference-doc が無い文書でレイアウトを書き換える経路が未確定
  （2 回変換 / 出力 `slideLayout*.xml` の後処理 / slide 経路のみ）
- **持ち込みテンプレートの autofit。** 既定テンプレートで `normAutofit` を持つのは
  マスターのタイトル枠だけなので、既定のままなら slide 経路の注入で自動縮小は起きない。
  **autofit を持つテンプレートを持ち込んだ場合だけが未検証**
- **docx の 1×N 表の Word 実機での見え方**（XML 上は罫線が 1 本も出ないことは確認済み）
- **`{#s-xxxx}` の可搬性コスト。** pptx の出力には現れないが、CommonMark / GFM のリーダーでは
  見出しに literal のまま見える。`::: columns` のフェンス行も同じ。
  どちらも「原稿は汚れる」という事実を README に正しく書く
- **文字サイズ設定と `szLvl` の関係。** 設定が絶対値のままだと、段組み（2100）や
  `Content with Caption`（title 1500）で設定値と描画が食い違う。
  設定を「解決値に対する倍率」へ変える必要があるか未決
- **縦書きと段組みの併用。** pandoc 既定テンプレートには `Vertical Title and Text`
  （`orient="vert"`）があるが、縦書きで段組みしたときの列の並び順（右→左になるか）は未検証
- **スライド寸法が変わったときの `Placement`**（EMU 絶対か割合か）
