# 検証ログ

企画検証の経緯。結論だけ必要なら `../CLAUDE.md` を読むこと。

## 1. pandoc.wasm は iPad で動くか → 動く

pandoc 3.9（2026年2月）で公式 WASM ビルドが提供された。
pandoc.org/app を iPad Safari で開いて Markdown → pptx が通ることを確認。
変換時間は体感ゼロ。

最初に出たエラーは WASM 由来ではなく、スライド区切りの `---` が
YAML メタデータブロックとして解釈されたもの。デスクトップ版と同一のエラーメッセージだった。
つまりエラーが出たこと自体が、パーサが正常動作している証拠だった。

## 2. 日本語 pptx は開けるか → 開ける

出力された pptx を iPad の Keynote / PowerPoint で開き、日本語の文字化けがないことを確認。

## 3. 規模テスト → 52枚

`fixtures/pptx-benchmark.md`（50枚規模）を pandoc 3.9 で変換して 52 枚。
手元の pandoc 3.1.3 では 64 枚。差分 12 枚の内訳は「表の後ろのスライド分割 11枚」と
「末尾の Notes スライド 1枚」と推定される。要確認。

RawBlock 警告（HTML コメント）が1件出たが、変換自体は成功。

## 4. reference-doc → 検証中

日本語版 PowerPoint のテンプレートはレイアウト名が一致せず、
pandoc 標準レイアウトに差し替わることをデスクトップで確認済み。
テーマ（配色・フォント）は引き継がれるが、プレースホルダ位置は失われる。

`docs/index.html` でレイアウト名を書き換えてから渡す方式を実装した。
iPad 実機での確認は未実施。

## 5. WASM ヒープは連続変換で増え続けるか → 増えるが想定よりずっと遅い

`docs/index.html` の「100回連続変換」を 50枚デッキで実行:

| 初回 | 中央値 | 直近5回 | ヒープ | 増分 |
|---|---|---|---|---|
| 243 ms | 169 ms | 167 ms | 114 MB | +7.6 MB |

1回あたり約 78 KB。ハーネスの判定は 64 KB/回 を境に最も厳しいバケットへ落ちるので
「定期的なインスタンス再生成が必要」と出るが、境界の 1.2 倍でしかない。
懸念していた 1MB/回 とは桁が違う。

変換時間は劣化しなかった。直近5回の平均が中央値を下回っている。
初回の 243ms だけ突出しているのは JIT ウォームアップ。

ただし測ったのは全体変換で、ライブプレビューが実際に回すのは1枚だけの変換。
増加が入力サイズに比例するのか呼び出しごとの固定費なのかは分かっていない。
また `heap0` を初回変換の前に測っている以上、一度きりの初期化コストが
7.6 MB に混ざって全回数で割られている。N を上げて曲線の形を見る必要がある。

結論としては、単一インスタンスを使い回し、ヒープ量が閾値を超えたら
裏で暖めておいた控えと差し替える方針で足りる見込み。
