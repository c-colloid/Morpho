# 検証ログ

企画検証の経緯。結論だけ必要なら `../CLAUDE.md` を読むこと。

## 1. pandoc.wasm は iPad で動くか → 動く

pandoc 3.9（2026年2月）で公式 WASM ビルドが提供された。
pandoc.org/app を iPad Safari で開いて Markdown → pptx が通ることを確認。
変換時間は体感ゼロ。

最初に出たエラーは WASM 由来ではなく、スライド区切りの `---` が
YAML メタデータブロックとして解釈されたもの。デスクトップ版と同一のエラーメッセージだった。
つまりエラーが出たこと自体が、パーサが正常動作している証拠だった。

## 2. 日本語 pptx は開けるか → 開ける

出力された pptx を iPad の Keynote / PowerPoint で開き、日本語の文字化けがないことを確認。

## 3. 規模テスト → 52枚

`fixtures/pptx-benchmark.md`（50枚規模）を pandoc 3.9 で変換して 52 枚。
手元の pandoc 3.1.3 では 64 枚。差分 12 枚の内訳は「表の後ろのスライド分割 11枚」と
「末尾の Notes スライド 1枚」と推定される。要確認。

RawBlock 警告（HTML コメント）が1件出たが、変換自体は成功。

## 4. reference-doc → 検証中

日本語版 PowerPoint のテンプレートはレイアウト名が一致せず、
pandoc 標準レイアウトに差し替わることをデスクトップで確認済み。
テーマ（配色・フォント）は引き継がれるが、プレースホルダ位置は失われる。

`docs/index.html` でレイアウト名を書き換えてから渡す方式を実装した。
iPad 実機での確認は未実施。

## 5. WASM ヒープは連続変換で増え続けるか → 増えない。頭打ちする

`docs/index.html` の「100回連続変換」を 50枚デッキで実行:

| | 初回 | 中央値 | 直近5回 | ヒープ | 増分 | 1回あたり |
|---|---|---|---|---|---|---|
| Windows デスクトップ | 243 ms | 169 ms | 167 ms | 114 MB | +7.6 MB | 78 KB |
| iPad（1回目） | 236 ms | **47 ms** | 46 ms | 114 MB | +76.8 MB | 0.77 MB |
| iPad（2回目・リロードなし） | 83 ms | 46 ms | 46 ms | 115 MB | +0.6 MB | 6.4 KB |

### 経緯

1回目の iPad の結果（0.77 MB/回）はハーネスの最も厳しい判定に落ち、
そのままなら 512 MB 上限で残り約 520 回、ライブプレビューでは
十数分の編集で使い切る計算だった。

しかし増加率が 10 倍違うデスクトップと iPad が、どちらも 114 MB で
着地しているのが引っかかった。1回ごとに漏れているなら同じ値に
揃う理由がない。開始値を逆算すると デスクトップ 106 MB / iPad 37 MB で、
「同じ上限へ向かって伸びているだけ」なら辻褄が合う。

リロードせずに2回目を回して確認したところ、増分が 76.8 MB → 0.6 MB、
**約 120 分の1** に落ちた。立ち上がりであってリークではないと確定。

`heap0` をソーク開始時に測る仕様上、立ち上がりの一度きりの確保が
増分に混ざって N で割られるため、初回のソークは実態より悪く出る。

### 結論

インスタンスは1つ作って使い回す。閾値監視も控えの暖機も差し替えも要らない。
定常状態のリニアメモリは約 115 MB。

残る 6.4 KB/回 が仮に本物の漏れでも、512 MB まで約 63,000 回ある。
毎秒2回変換し続けて 8.8 時間。設計判断は変わらないので追加測定はしない。

### 副産物

リニアメモリだけで 115 MB あるため、App Extension の約 120 MB 制限は
モジュール本体（55.9 MB）を数える前に埋まる。
「変換は本体プロセスで行う」が推測から実測に変わった。

### iPad が 3.6 倍速い

同じ wasm をブラウザで回して iPad がデスクトップに勝った（47 ms vs 169 ms）。
デスクトップ版 pandoc 3.1.3 のネイティブ実行（216 ms / 64枚）よりも速い。
全体変換だけで対話的な速度に収まるため、「カーソルのあるスライドだけ変換する」
二層構造は 50枚規模では初期実装の必須要件ではなくなった。

JIT ウォームアップは実機の方が大きい（iPad 236→47ms の5倍、
デスクトップ 243→169ms の1.4倍）。
さらに2回目のソークは温まった状態から始めたのに初回だけ 83 ms かかっており、
アイドル後の最初の変換にも復帰コストがある。

## 6. WASM 上で Lua フィルタは動くか → 動く。日本語記法レイヤは実装可能

2段階で確認した。

1. **実機（iPad / RN WebView）**: HTML コメントを除去する strip.lua を
   filters で渡して変換。RawBlock 警告が消えた。フィルタは実機の wasm で動く。
2. **Node（pandoc-wasm 1.1.0）**: 青空文庫式ルビ ｜漢字《かんじ》 を
   親文字（よみ）に落とすフィルタが通った。多バイト文字の gsub も動く。

### Lua パターンの落とし穴（実測）

Lua のパターンはバイト単位で動くため、多バイト文字を含む否定文字クラスは壊れる。

| パターン | 結果 |
|---|---|
| `s:gsub("｜", "…")`（リテラル） | ○ |
| `s:gsub("｜(.-)《(.-)》", "%1（%2）")`（遅延量指定子） | **○ これを使う** |
| `s:gsub("｜([^《]-)《…")`（否定クラス） | ✗ 《=E3 80 8A の否定が E3 で始まるひらがな全部を弾く |

日本語記法レイヤ（ルビ・傍点）は pandoc.wasm 上の Lua フィルタで実装できる。
出力形式ごとの表現（docx は w:ruby の RawInline、pptx は括弧書きへのフォールバック等）は
writer 側の設計と合わせて決める。


## 7. プリセット図形のテキスト矩形は外接矩形と一致しない → 原典から導出して確定

装飾のテキスト（番号バッジ等）が「プレビューでは図形の中心・pptx では別の位置」に
出る問題の原因。OOXML のプリセット図形は presetShapeDefinitions.xml で
図形ごとに固有の <rect>（テキストを配置する内接領域）を定義しており、
PowerPoint は文字をその矩形に対して配置する。

既定 adj で評価した結果（実測ではなく原典の式の評価。w×h に対する比率）:

| 図形 | テキスト矩形 | 外接中心とのずれ |
|---|---|---|
| rect | 全域 | なし |
| roundRect | 四辺 0.048815×短辺 の内側 | なし |
| ellipse | 各軸 14.6447% 内側 | なし |
| triangle | (w/4, h/2)〜(3w/4, h) | 下へ h/4 |
| diamond | (w/4, h/4)〜(3w/4, 3h/4) | なし |
| hexagon | q8=2+2·ss/w、各軸 q8/24 内側 | なし |
| star5 | (0.3090w, 0.3820h)〜(0.6910w, 0.7639h) | 下へ 0.073h |
| rightArrow | (0, h/4)〜(w−ss/4, 3h/4) | 左へ ss/8 |

対処（CLAUDE.md の「出力が真実」原則どおり）:
`src/design/shapeGeometry.ts` の textRect にこの評価値を実装し、
プレビューの文字をテキスト矩形の中心に置く。書き出し側は
`bodyPr wrap="none" anchorCtr="1"` で折り返しを止め、1行表示のプレビューと
挙動を揃える。検証は check-design（原典評価値との突き合わせ）。


## 8. タイトル・本文テキストの位置ずれ → マスターの3値をプレビューが読んでいなかった

「図形（装飾）は合っているのに文字だけずれる」実機報告の後半。
装飾テキスト（findings 7）とは別に、通常のタイトル・本文にも系統的なずれがあった。
pandoc 既定マスターを dump して実測した結果:

| 項目 | 実出力（マスター） | 旧プレビュー |
|---|---|---|
| タイトルの垂直アンカー | `bodyPr anchor="ctr"`（中央） | 下揃え（決め打ち） |
| タイトルの水平揃え | `titleStyle lvl1 algn="ctr"`（中央） | 左揃え |
| 本文の段落前間隔 | `spcBef spcPct 20000`（行高の 20%・全階層） | 0 |
| 枠内余白 | lIns/rIns=91440, tIns/bIns=45720 | 一致していた |

対処: パーサが bodyPr の anchor（スライド → レイアウト → マスターの継承）、
pPr / スタイルの algn、bodyStyle の spcBef を読み、プレビューが適用する。
残る差はフォントメトリクス由来の行折り返し（既知の近似・CLAUDE.md 記載）。


## 9. 残っていたズレ2件 — 行頭記号の buChar と、あふれの扱い

0.6.8 の後も実機比較（PowerPoint iPad で出力を開いた画面）で残っていた差。
なお同じスクリーンショットの実測では、行送り（約1.25em）と段落前間隔は
プレビューの定数とほぼ一致していた。

| 項目 | 実出力 | 旧プレビュー |
|---|---|---|
| 行頭記号 | マスターの buChar。pandoc 既定は階層ごとに • – • – … の交互 | • と ◦ の決め打ち |
| 枠に収まらないテキスト | 切らずにあふれる（スライド端も越える） | 枠で切り捨て（overflow hidden） |

対処: buChar を bodyStyle の lvl ごとに読んでプレビューが使う。
あふれは枠では切らず、スライド端（surface）でだけ切る —
「出力には見えるのにプレビューに無い行」をなくし、収まっていないことが
プレビューで分かるようにする。
残る差はフォントメトリクス由来の行折り返し位置のみ（既知の近似）。


## 10. PowerPoint が「ファイルを開けません」— 原因は原稿コピペ由来の U+000B

実機報告「0.6 のどこかから pptx 出力が PowerPoint で開けなくなった」の調査。
結論から言うと**アプリのバージョンは無関係**で、原稿の内容が引き金だった。

切り分けの経緯:

1. 0.6.8（出力が開けていた最後の確認点）以降で書き出しバイト列に触れる変更は
   0.7.0 の applyTextSizes だけと git で確定
2. アプリと同一経路（pandoc-wasm 1.1.0 + 後処理）で合成データを大量生成し、
   XML 整形式・python-pptx・LibreOffice（PDF 変換まで）・ECMA-376 XSD 厳密検証・
   Open XML SDK バリデータの全部に通した → **全部妥当。再現せず**
3. ユーザー提供の実原稿で再生成 → Open XML SDK バリデータだけが検出:
   `hexadecimal value 0x0B, is an invalid character`（slide1.xml）

原稿の front matter の author 行（NEJM サイトからのコピペ）に
U+000B（垂直タブ）が入っていた。ページ上は改行に見える文字。
pandoc はこれをエスケープも除去もせず slide XML へ素通しし、
XML 1.0 の禁止文字なので PowerPoint がファイルごと拒否する。
**LibreOffice / python-pptx / lxml は黙って通す**（だから 2. で捕まらなかった）。

対処（0.8.2）: 変換境界（pandoc へ渡す直前の sanitizeForXml）で metadata と
本文の両方から XML 非対応文字を空白へ 1:1 置換（本文オフセット保持）。
splitFrontMatter 自体は原稿に忠実なまま — ノート編集・改行編集の書き戻しが
原稿（外部ファイル含む）を書き換えないようにするため。
教訓: pptx の検証は Open XML SDK 系（npm: @ooxml-tools/validate）でないと
PowerPoint の判定を代弁できない。


## 11. フッター（出典・注釈）の実測 — 設計は `notes/footer-design.md`

「出典や注釈を小さくかけるフッター」の設計にあたって、pandoc-wasm 1.1.0（3.10 相当）の
実出力を 8 方向から測った。結論と設計は `notes/footer-design.md`、再現は
`app/scripts/dump-footer.mjs`。ここには経緯と、他の機能にも効く発見だけを残す。

### 期待と逆だったこと

**pptx にはフッター枠が最初からあり、docx には無かった。**
pandoc 既定 reference の 11 レイアウトすべてが `ftr` / `dt` / `sldNum` を持ち、
マスターに座標（y=92.69%・高さ 5.32%・9pt・中央揃え）まで入っている。
一方 docx には `word/footer*.xml` もスタイルも 0 個で、本文 12pt より小さい段落スタイルは
`Abstract` / `AbstractTitle` の 10pt しか存在しない。
「スライドは自作、文書は pandoc 任せ」という直感と逆だった。

それでも ftr プレースホルダは使わない判断にした。理由は
`findInherited` が type / idx で外れると **body の枠へ落ちる**ため、
ftr を持たないテンプレートでフッターが本文全面に化けること（実測・警告ゼロ）が最大。
落とし穴 4 と同じ「色は合っているのに配置が違う」壊れ方をする。

### スライド番号は数えてはいけない

`fixtures/pptx-benchmark.md` で `cursorSlide.ts` は 9 枚と数え、pandoc は 64 枚を出した。
主因は表の分割ではなく **pandoc の slide level 自動判定**で、`#` の直下に `##` を置くと
slide level が 2 になり `##` がスライドを作る。抄読会の原稿はまさにこの形。

代わりに、Lua で私用領域文字（U+E001 / U+E002）の目印を打ち、
OOXML 後処理で「pandoc が実際に置いたスライド」を読む。
ただし**目印を本文の Para として置くと 7 件中 3 件がずれ、デッキが 1 枚増える**。
**直前の見出しの inline 末尾へ巻き上げる**と benchmark で 7/7 正解し、
スライド数もレイアウト内訳も 1 バイトも変わらなかった。

### 検証器は較正しないと沈黙に気づけない

`@ooxml-tools/validate`（落とし穴 9 で唯一 PowerPoint の判定を代弁できた検証器）は
**default export が本体**で、README の 2 引数シグネチャは古い。
「素の出力 0 件 / 注入後 0 件」だけでは何も言えないので、
**子要素順をわざと壊した較正ケース**を同居させる（1 件出ることを確認済み）。
同じ手順で `xmldom` の整形式性チェックを較正したところ、信号がまったく出ないと分かった。

### ついでに見つかった既存の不具合（未修正）

1. **文書全体の設定（文字サイズ・テンプレート配線盤）が典型的な原稿で開けない。**
   `DecorSheet` の入口が `contentIndexOf` を通り、`slideCount - titleOffset` と
   `slideSegments(body).length` が一致しないと Alert で止まる。`#` の下に `##` を置く
   普通の階層構造では必ず発火する（15 行の原稿で 6 対 2、benchmark で 63 対 8）
2. **`designFile.ts` の `sanitizeDecorText` が 3 つ同時に壊れている。**
   U+FFFE を素通しし（注入した pptx がスキーマ検証 1 件になる）、XML 1.0 で合法な
   U+007F を落とし、20 字で切る。`frontMatter.ts` の `XML_INVALID_RE` と共通化すべき
3. **`titleOffset = metadata.title ? 1 : 0` が誤り。** 表紙は `author` / `subtitle` / `date`
   のどれか単独でも生える
4. **表紙の日付が 24pt で描かれている。** `dt` は `isTitle` / `isCover` / `isSub` の
   どれにも当たらず `bodySz[0]` になるが、枠の高さは 21.6pt
