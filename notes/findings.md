# 検証ログ

企画検証の経緯。結論だけ必要なら `../CLAUDE.md` を読むこと。

## 1. pandoc.wasm は iPad で動くか → 動く

pandoc 3.9（2026年2月）で公式 WASM ビルドが提供された。
pandoc.org/app を iPad Safari で開いて Markdown → pptx が通ることを確認。
変換時間は体感ゼロ。

最初に出たエラーは WASM 由来ではなく、スライド区切りの `---` が
YAML メタデータブロックとして解釈されたもの。デスクトップ版と同一のエラーメッセージだった。
つまりエラーが出たこと自体が、パーサが正常動作している証拠だった。

## 2. 日本語 pptx は開けるか → 開ける

出力された pptx を iPad の Keynote / PowerPoint で開き、日本語の文字化けがないことを確認。

## 3. 規模テスト → 52枚

`fixtures/pptx-benchmark.md`（50枚規模）を pandoc 3.9 で変換して 52 枚。
手元の pandoc 3.1.3 では 64 枚。差分 12 枚の内訳は「表の後ろのスライド分割 11枚」と
「末尾の Notes スライド 1枚」と推定される。要確認。

RawBlock 警告（HTML コメント）が1件出たが、変換自体は成功。

## 4. reference-doc → 検証中

日本語版 PowerPoint のテンプレートはレイアウト名が一致せず、
pandoc 標準レイアウトに差し替わることをデスクトップで確認済み。
テーマ（配色・フォント）は引き継がれるが、プレースホルダ位置は失われる。

`docs/index.html` でレイアウト名を書き換えてから渡す方式を実装した。
iPad 実機での確認は未実施。

## 5. WASM ヒープは連続変換で増え続けるか → 増えない。頭打ちする

`docs/index.html` の「100回連続変換」を 50枚デッキで実行:

| | 初回 | 中央値 | 直近5回 | ヒープ | 増分 | 1回あたり |
|---|---|---|---|---|---|---|
| Windows デスクトップ | 243 ms | 169 ms | 167 ms | 114 MB | +7.6 MB | 78 KB |
| iPad（1回目） | 236 ms | **47 ms** | 46 ms | 114 MB | +76.8 MB | 0.77 MB |
| iPad（2回目・リロードなし） | 83 ms | 46 ms | 46 ms | 115 MB | +0.6 MB | 6.4 KB |

### 経緯

1回目の iPad の結果（0.77 MB/回）はハーネスの最も厳しい判定に落ち、
そのままなら 512 MB 上限で残り約 520 回、ライブプレビューでは
十数分の編集で使い切る計算だった。

しかし増加率が 10 倍違うデスクトップと iPad が、どちらも 114 MB で
着地しているのが引っかかった。1回ごとに漏れているなら同じ値に
揃う理由がない。開始値を逆算すると デスクトップ 106 MB / iPad 37 MB で、
「同じ上限へ向かって伸びているだけ」なら辻褄が合う。

リロードせずに2回目を回して確認したところ、増分が 76.8 MB → 0.6 MB、
**約 120 分の1** に落ちた。立ち上がりであってリークではないと確定。

`heap0` をソーク開始時に測る仕様上、立ち上がりの一度きりの確保が
増分に混ざって N で割られるため、初回のソークは実態より悪く出る。

### 結論

インスタンスは1つ作って使い回す。閾値監視も控えの暖機も差し替えも要らない。
定常状態のリニアメモリは約 115 MB。

残る 6.4 KB/回 が仮に本物の漏れでも、512 MB まで約 63,000 回ある。
毎秒2回変換し続けて 8.8 時間。設計判断は変わらないので追加測定はしない。

### 副産物

リニアメモリだけで 115 MB あるため、App Extension の約 120 MB 制限は
モジュール本体（55.9 MB）を数える前に埋まる。
「変換は本体プロセスで行う」が推測から実測に変わった。

### iPad が 3.6 倍速い

同じ wasm をブラウザで回して iPad がデスクトップに勝った（47 ms vs 169 ms）。
デスクトップ版 pandoc 3.1.3 のネイティブ実行（216 ms / 64枚）よりも速い。
全体変換だけで対話的な速度に収まるため、「カーソルのあるスライドだけ変換する」
二層構造は 50枚規模では初期実装の必須要件ではなくなった。

JIT ウォームアップは実機の方が大きい（iPad 236→47ms の5倍、
デスクトップ 243→169ms の1.4倍）。
さらに2回目のソークは温まった状態から始めたのに初回だけ 83 ms かかっており、
アイドル後の最初の変換にも復帰コストがある。
