# 検証ログ

企画検証の経緯。結論だけ必要なら `../CLAUDE.md` を読むこと。

## 1. pandoc.wasm は iPad で動くか → 動く

pandoc 3.9（2026年2月）で公式 WASM ビルドが提供された。
pandoc.org/app を iPad Safari で開いて Markdown → pptx が通ることを確認。
変換時間は体感ゼロ。

最初に出たエラーは WASM 由来ではなく、スライド区切りの `---` が
YAML メタデータブロックとして解釈されたもの。デスクトップ版と同一のエラーメッセージだった。
つまりエラーが出たこと自体が、パーサが正常動作している証拠だった。

## 2. 日本語 pptx は開けるか → 開ける

出力された pptx を iPad の Keynote / PowerPoint で開き、日本語の文字化けがないことを確認。

## 3. 規模テスト → 52枚

`fixtures/pptx-benchmark.md`（50枚規模）を pandoc 3.9 で変換して 52 枚。
手元の pandoc 3.1.3 では 64 枚。差分 12 枚の内訳は「表の後ろのスライド分割 11枚」と
「末尾の Notes スライド 1枚」と推定される。要確認。

RawBlock 警告（HTML コメント）が1件出たが、変換自体は成功。

## 4. reference-doc → 検証中

日本語版 PowerPoint のテンプレートはレイアウト名が一致せず、
pandoc 標準レイアウトに差し替わることをデスクトップで確認済み。
テーマ（配色・フォント）は引き継がれるが、プレースホルダ位置は失われる。

`docs/index.html` でレイアウト名を書き換えてから渡す方式を実装した。
iPad 実機での確認は未実施。

## 5. WASM ヒープは連続変換で増え続けるか → 判断保留（頭打ちの疑いが濃い）

`docs/index.html` の「100回連続変換」を 50枚デッキで、2機種で実行:

| | 初回 | 中央値 | 直近5回 | ヒープ | 増分 | 1回あたり |
|---|---|---|---|---|---|---|
| Windows デスクトップ | 243 ms | 169 ms | 167 ms | 114 MB | +7.6 MB | 約 78 KB |
| iPad | 236 ms | **47 ms** | 46 ms | 114 MB | +76.8 MB | 約 0.77 MB |

### iPad が 3.6 倍速い

同じ wasm をブラウザで回して、iPad がデスクトップに勝った。
50枚デッキの全体変換が 47 ms。デスクトップ版 pandoc 3.1.3 のネイティブ実行
（216 ms / 64枚）と比べても速い。

結果として、全体変換だけでも対話的な速度に収まっている。
「カーソルのあるスライドだけ変換する」二層構造は 50枚規模では必須ではなくなった。

JIT ウォームアップは実機の方が遥かに大きい。iPad は 236 → 47 ms で5倍、
デスクトップは 243 → 169 ms で1.4倍。起動時のダミー変換は実機でこそ効く。

### 増分 10 倍の差より、着地点が一致していることの方が重要

1回あたりの増加は iPad が 10 倍悪い。しかし**両機種とも 114 MB で止まっている**。
開始時点を逆算すると デスクトップ 106 MB / iPad 37 MB。

増加率が 10 倍違うものが同じ値に着地するのは、漏れているのではなく
同じ上限へ向かって伸びているから、と考えるのが自然。
GHC ランタイムがこのワークロードで要求する作業領域が約 114 MB あり、
デスクトップは（ソーク前に手動変換を何度か回していたため）既にそこに近く、
iPad はほぼ新品から始めた — これで辻褄が合う。

`heap0` をソーク開始時に測る仕様上、立ち上がりの一度きりの確保が
増分に混ざって N で割られる。この解釈が正しければ、
デスクトップの 78 KB/回 の方が定常状態に近い。

### 判別テスト

iPad でリロードせずにソークを2回続けて押す。
2回目の増分が落ちれば頭打ち、変わらなければ本物の線形リーク。
線形だった場合、512 MB 上限で残り約 520 回しかなく、
ライブプレビューでは十数分で使い切る。実装前にここを確定させる。
