# 段組みの入力 — 設計のやり直し

`columns-and-images.md` は「記法は pandoc ネイティブの `::: {.columns}` をそのまま使い、
UI は挿入を楽にする」という前提で書いた。**その前提が作者本人の使用で否定された** —
「そもそもカラムの入力が難しすぎて把握していなかった」。

やり直した設計。技術事実は pandoc-wasm 1.1.0（= pandoc 3.10）を Node から回した実測。
**実機 iPad での見え方は未検証。**

---

## なぜやり直すか

最小の 2 段スライドは、pandoc ネイティブ記法だと**構造だけで 8 行**（うち 6 行は記号のみ）:

```
::: {.columns}
::: {.column}
左
:::
::: {.column}
右
:::
:::
```

半角記号は 5 種（`:` `{` `}` `.` 空白）。現実的な 16 通りの書き方を通した結果、
**意図どおり 2 段になるのは 4 つだけ**だった。

| 書き方 | 結果 | 非 INFO 警告 |
|---|---|---|
| 正解 | ○ Two Content | 0 |
| `::: columns` / `::: column`（波括弧なし 1 語） | ○ Two Content | 0 |
| 外側の閉じ忘れ | ○ Two Content | **1** |
| 柵の間に空行 | ○ Two Content | 0 |
| **全角波括弧 `｛.columns｝`** | × 1 段。**本文は正常に出る** | **0** |
| **全角スペース** | × 1 段。**本文は正常に出る** | **0** |
| **ドット忘れ `{columns}`** | × 1 段。**本文は正常に出る** | **0** |
| **クラス名タイポ `{.colums}`** | × 1 段。**本文は正常に出る** | **0** |
| **`.column` を書かない** | × 1 段。**本文は正常に出る** | **0** |
| 全角コロン `：：：` | × 記法が生のまま本文に出る | 0 |
| コロン 2 個 `::` | × 記法が生のまま本文に出る | 0 |
| 波括弧なし 2 語 `::: columns compare` | × 記法が生のまま本文に出る | 0 |
| 字下げして書く | × 内側の柵が生のまま本文に出る | 0 |
| 内側の閉じ忘れ | × 生の柵が混じる | 0 |
| 閉じが 1 つ多い | × 2 枚に割れる | 0 |
| 3 列 | 3 列目が消える | 0（INFO 1） |

**太字の 5 件が最悪。** 本文は正しく出るので、書き手には「なぜか 2 段にならない」以外の
手がかりが無い。しかも**全角波括弧と全角スペースは日本語 IME で普通に起きる**。

Morpho の Diagnostic は変換器の警告を分類して出す作りなので、
**警告が出ない失敗は原理的に伝えられない**。

さらに、正しく打てても「段組みはスライド区間の中で唯一のブロックでなければならない」
（外れるとスライドが割れ、`contentIndexOf` が文書全体で null を返す）という制約が残る。

### このプロジェクトは同じ失敗を繰り返している

`app/README.md` の記法表には既にこう書いてある:

- 行末 `\` は「**日本語キーボードでは `¥` が入力されることがあり、`¥` では効かない**」
- 箇条書きの入れ子は「**半角1つでは入れ子にならず、全角スペースだと箇条書き自体が壊れる**」

「日本語キーボードで半角記号を正確に打たせる」設計が繰り返し破綻している。
段組みはその中で**最も記号が多い記法**だった。

## 決定事項

| 論点 | 決定 | 根拠 |
|---|---|---|
| 記法 | **`+++`（列区切り）を内容層に足す。** `+++` が n 個 → n+1 列 | 8 行・記号 6 行・半角 5 種 → **1 行 3 文字・半角 1 種**。ルビ `{漢字\|かんじ}`・傍点 `《《…》》` で既に採った「劣化しても日本語の書き手には読める独自記法」と同じ基準 |
| pandoc ネイティブ記法 | **捨てない。** `::: {.columns}` も従来どおり受け付ける | 他所からコピペした原稿・可搬性を重視する書き手のため |
| 区切り記号に `+++` を選んだ理由 | pandoc の markdown で**ただの段落**として素通りする（`<p>+++</p>`・行頭記号にならず警告 0。実測）。`***`（スライド区切り）と対になる語彙で、どちらも半角記号 3 個 | `---` は front matter と衝突（落とし穴 1）、`===` は setext 見出しの下線、`\|\|\|` は表記法と紛らわしい |
| 展開の規則 | **スライド区間の中に `+++` が 1 つでもあれば、その区間の本文まるごとを列に割る**（見出しと末尾の `::: notes` は外に出す） | 「段組みの外に本文がある」状態が**原理的に作れない**ので、pandoc の「無警告で消える / スライドが割れる」を構造的に回避する（実測） |
| 打ち間違いの救済 | 変換直前の正規化で全角・スペース入りを吸収する。**原稿ファイルは書き換えない** | `sanitizeForXml` と同じ置き場所・同じ作法（落とし穴 9） |
| 沈黙の禁止 | 段組みに関する失敗は**変換器の警告に頼らず Morpho 自身が診断する** | 列数は変換前に数えられる。pandoc の INFO 警告を待つ必要が無い |
| UI | 挿入は**1 行**なので `blockInsert.ts`（v0.14）にそのまま乗る | 8 行の骨組みを入れるより桁違いに安い |
| 原稿に残るもの | `+++` の 1 行 | Obsidian・素の pandoc では `+++` が見えるだけで、**本文は全部読める**（1 段に流れる） |

## 記法

```markdown
# 三つの案

案A の説明

+++

案B の説明

+++

案C の説明
```

- `+++` は**列区切り**。n 個で n+1 列
- 閉じ不要・入れ子なし
- 見出し（`#`）はスライドのタイトルとして列の外に残る
- 末尾の `::: notes` も列の外に残る
- コードフェンスの中の `+++` と、インラインの `` `+++` `` は**区切りにならない**（実測）

### 受け付ける揺れ（正規化）

| 書き方 | 扱い | 理由 |
|---|---|---|
| `+++` `++++` `+++++` | 区切り | 3 個以上 |
| `＋＋＋`（全角） | 区切り | 日本語 IME で普通に起きる。実測でも pandoc はただの段落として素通りするので、正規化しないと 1 段のまま無警告 |
| `+ + +`（スペース入り） | 区切り | **pandoc はこれを痕跡なく消す**（実測: 本文から行ごと消え、警告 0）。救わないと最悪の沈黙になる |
| 行頭・行末の空白 | 区切り | |
| `++ +` | 区切りにしない | 本文にそのまま出るので、失敗が見える |

判定は `^[ \t]*[+＋]([ \t]*[+＋]){2,}[ \t]*$`。

## 展開の規則

原稿は書き換えない。変換へ渡す文字列だけを作る。

```
1. 本文をスライド区間に切る（境界は行頭 `# ` と水平線。cursorSlide.ts と同じ規則）
2. 区間ごとに、コードフェンスの外・`::: notes` の外にある `+++` を数える
3. 1 つも無ければ何もしない
4. あれば:
     見出し行と先頭の空行  → そのまま前に置く
     末尾の `::: notes` 〜 → そのまま後ろに置く
     残り（区間の本文全部） → `+++` で分割し、各片を 1 列にする
```

**この規則の要点は「区間の本文まるごと」を割ること。** 導入の段落があっても、
それは左の列に入るだけで、段組みの外には出ない。だから
pandoc ネイティブ記法で起きる「段組みの前後に別の内容があるとスライドが割れる」が
**構造的に起きない**。

pandoc バックエンドはこの構造を fenced div へ実現する。
自前 writer（MIT）に替えるときは、同じ構造を writer が直接受ければよい
（`+++` の走査結果は pandoc の語彙を含まない）。

## 検証結果

19 ケースを本物の pandoc.wasm に通した。**全ケースで
「pandoc のスライド数 = `slideSegments` の区間数」が一致**する（＝ `contentIndexOf` が死なない）。

| ケース | 結果 |
|---|---|
| 基本（左 `+++` 右） | 1 枚 Two Content・非 INFO 警告 0 |
| **導入つき**（pandoc 記法なら 2 枚に割れて編集が止まる形） | **1 枚**。導入が左列に入る |
| 全角 `＋＋＋` | 1 枚（正規化で救済） |
| `::: notes` つき | 1 枚。ノートは列の外 |
| 箇条書きを列に | 1 枚。左右とも行頭記号が付く |
| 画像を列に | 1 枚。画像が左列に入る |
| 表を列に | 1 枚。出力の pptx に `graphicFrame` が 1 つ入る（**プレビューに出ないのは A-5 の未実装**であってデータロスではない） |
| ルビ・傍点を列に | 1 枚。記法が壊れない |
| 左が空 / 右が空 / `+++` が連続 | 1 枚。空の列になるだけ |
| コードフェンスの中の `+++` | 区切りにならない。本文に出る |
| `` `+++` ``（インラインコード） | 区切りにならない |
| front matter あり | 表紙 + 段組み = 2 枚。一致 |
| `***` 区切りと併用 | 2 枚。一致 |
| 見出しなし区間（`***` だけで作った区間） | 一致 |
| 複数スライドに段組みが混在 | 一致 |
| 3 列 | 下記 |

### 3 列以上の刷り分け

列区切りなので 3 列以上が書ける。**内容が失われるのは pptx だけ**（実測）:

| 形式 | 3 列 |
|---|---|
| pptx | **2 列まで**。3 列目が消える（pandoc の痕跡は INFO 警告 1 件のみ） |
| html / Web / epub | **3 列とも出る**（`div.columns` + `div.column` ×3。pandoc 既定 CSS の flex で 3 段になる） |
| docx | 内容は全部残る（列は消えて 1 段に流れる。警告 0） |

診断は**形式を名指しする**: 「スライドでは 3 列目以降が出ません。Web では 3 列で出ます」。
列数は変換前に数えられるので、**pandoc の警告を待たずに出せる**。
これが現状（INFO 1 件が「その他の情報」に埋もれる）との決定的な差。

## 打ち間違いの救済と診断

### 救済（正規化）

変換直前に、原稿ファイルを書き換えずに次を吸収する。

- `+++` 系の揺れ（上表）
- pandoc ネイティブ記法を手で書いた場合の全角コロン・全角波括弧・全角スペース・
  ドット忘れ・クラス名の近いタイポ・字下げ

正規化は**コードフェンスの中では行わない**（記法そのものを説明する原稿があるため）。

### 診断（沈黙をなくす）

Morpho 自身が出す。変換器の警告に依存しない。

| 状況 | 重要度 | 文面の要点 |
|---|---|---|
| 3 列以上を書いた | 要対応 | スライドでは 3 列目以降が出ない。Web では出る |
| pandoc ネイティブ記法を正規化して救った | 情報 | 「`｛.columns｝` を `{.columns}` として扱いました」 |
| pandoc ネイティブ記法が段組みになっていない | 要対応 | どの行が原因か・`+++` で書き直す導線 |
| 列が空 | 情報 | |

## UI

`+++` は 1 行なので、挿入は v0.14 の `blockInsert.ts` にそのまま乗る。

- **入口**: プレビューの段落を長押し → 用途メニューに「ここで列を分ける」。
  原稿ペインのツールバー（画像ボタンの隣）に「段組み」
- **挿入**: カーソルのある段落の直後に `+++` を独立段落として入れる。
  `patchBody` を通す（front matter 保護・楽観ロック・Undo が一律で効く）
- **列を消す**: `+++` の行を消すだけ。書き手が手でできる
- **原稿ペインに見えるもの**: `+++` の 1 行だけ。**壊しようがない**。
  pandoc ネイティブ記法の「8 行の柵が見えていて、触ると壊れる」問題が消える

`+++` を打つ手段は 3 つある（UI・キーボードで `+` を 3 回・全角のまま）。どれでも通る。

## 判断の記録

- **独自記法を内容層に入れるか** → 入れる。ルビ・傍点と同じ「劣化しても読める」基準を満たし、
  可搬性で失うのは「他ツールで段組みにならない」だけ（本文は読める）
- **`+++` は列区切りか、左右の境界か** → **列区切り**。n 個で n+1 列。
  3 列以上は Web/epub で実際に出るので、書けること自体に意味がある

## リスクと未検証

- **実機（iPad）では一切試していない。** `+` を 3 回打つのが実際に楽かどうか、
  日本語キーボードで `+` がどのレイヤにあるかは未検証。
  `status-and-plan.md` の実機周回の受け入れ条件に足すこと
- **`+++` が本文として必要な原稿**（記法の説明文など）は、
  コードフェンスかインラインコードに入れる必要がある。実測ではどちらも区切りにならない
- **Obsidian で開いたときの見え方**は未検証（`+++` は Obsidian の記法ではないので
  そのまま表示されるはずだが、確認していない）
- **正規化の誤爆**は個別には測っていない。とくに
  「本文に本当に `｛.columns｝` と書きたい」ケースの扱い
- **展開の実装は試作段階**。`scratchpad` の試作で 19 ケースを通したが、
  本番の置き場所（変換器の内側 / `columns.ts` との分割）はまだ決めただけ
- **3 列以上のときのプレビュー**。スライドプレビューは実出力を読むので 2 列で描かれ、
  Web プレビューは 3 列で描かれる。**形式ごとに違って見えるのが正しい**が、
  書き手が混乱しないかは実機で見るまで分からない
