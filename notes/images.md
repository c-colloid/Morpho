# 画像がある場合の配置デザイン — 設計

画像をどこに・どれだけの大きさで置くかを**誰が決めるか**を確定する。
技術事実はすべて pandoc.wasm 1.1.0 の実出力と、リポジトリのコードを実際に叩いて確かめた。
確かめていないものは §9 に「何を測れば確定するか」つきで書く。

---

## 0. 出発点 — 一度否定して、実測で戻した前提

最初の調査は「画像の配置は pandoc のハードコードで、テンプレートでは動かせない」と結論した。
**これは誤りだった。** 反証の実測（`CLAUDE.md` 落とし穴 11 に反映済み）:

| 条件 | `<p:pic>` の off / ext |
|---|---|
| 素の出力（本文＋画像 = Content with Caption） | 3568700,1117600 / 5105400×2552700 |
| **layout8 の `ph idx="1"` を 1000000,1000000 / 2000000×1000000 に書き換え** | **990600,990600 / 1981200×990600** |
| 素の出力（画像だけ = Title and Content） | 1181100,1193800 / 6781800×3390900 |
| layout2 の枠を書き換え | 変化なし。**layout2 には `<a:off>` が1つも無い** |
| **マスターの `idx="1" type="body"` を同じ値に書き換え** | **990600,990600 / 1981200×990600** |

画像は**枠の内側に縦横比を保って収まる**。枠はレイアウト → マスターの継承で決まる。
「動かない」と見えたのは、pandoc 既定テンプレートの layout2 が座標を持たず、
**書き換えが空振りしていた**から。`<p:sldSz>` を 4:3 にしても動かないのも同じ理由
（プレースホルダ枠がスライド寸法に追従しない）で、ハードコードの証拠にはならない。

**この訂正が設計を変える。** PowerPoint 製のテンプレートはレイアウトに必ず座標を持つので、
配線盤経由のテンプレートでは**画像はすでにテンプレートに従っている**。
`asideRight` / `corner` / `bleed` の相当部分は段の幅比率とまったく同じく
**テンプレート層で解ける**。OOXML 後処理は「1枚だけ例外的に動かす」ぶんへ縮む。

（枠 → 画像の正確な換算式は未検証。§9-1）

## 1. 決定事項

| 論点 | 決定 | 根拠 |
|---|---|---|
| 大きさの指定 | **原稿には書かせない** | pptx では `{width=}` `{height=}` が完全に無視される（2in / 30% / 3in×1in で出力バイト数まで同一。実測）。同じ数値が形式ごとに違う意味を持つものを内容層に置くと刷り分けが崩れる |
| 配置クラス（`{.full}` `{.aside}`）を原稿に書かせるか | **書かせない** | Obsidian / GitHub は pandoc の属性を解さず、`{.aside}` が本文の文字として見える。ルビで「劣化しても日本語の書き手には読める」記法を選んだ理由と真逆。`{.full}` は座標の別名であって、roadmap v0.4 が原稿へ入れると決めた**意味クラス**ではない |
| **まずどこで解くか** | **テンプレート（レイアウトの枠）で解く。後処理は例外のためだけに使う** | §0。着手前に「Two Content / Content with Caption / Title and Content の枠を書き換えたテンプレートで、プリセットのうち何個が後処理ゼロで出せるか」を1回測る（§9-2） |
| 画像の同一性（アンカー） | **アセット名 + 同名画像の出現順**（`{ image: "airway.png", nth: 0 }`） | `saveAsset`（`store/assets.ts:24-41`）が文書内でフラット名の一意性を保証し、`parsePics`（`bridgeHtml.ts:311`）が `cNvPr descr` から元ファイル名を既に取っている。**新しい運搬路を発明せずに今日成立する**。スライド序数は画像1枚の追加で全部ずれる（画像はスライドを割る。実測） |
| 出力への痕跡（`{#im-xxxx}` / ファイル別名） | **どちらも採らない** | 別名で descr を書き換えると `SlideImage.name` が変わり、`imageUriOf`（`EditorScreen.tsx:441`）が保存庫を引けず**プレビューの画像が消える** |
| キャプション付き2枚の重なり | **リーダーの `-implicit_figures` で直す。後処理を書かない** | 実測: 現行リーダーでは1枚に pic 2つ＋`ph idx="1"` のキャプション枠2つが重なる。**`-implicit_figures` を付けると2枚に正しく割れ、キャプションも両方残る**。ただし `![説明](x.png)` がキャプション枠を持たなくなるので、採否は製品判断（§9-3） |
| スライドの結合（画像で割れた無題スライドを前へ繋ぐ） | **やらない** | `sldIdLst` / `_rels` / `[Content_Types].xml` の3箇所整合が要り、失敗形は落とし穴 9 と同じ「PowerPoint がファイルごと開かない」。割れる書き方をリントで事前に告げる |
| 無警告のデータロス | **純関数のリントで、変換を待たず打鍵直後に出す** | インライン画像・箇条書き内・同段落2枚・段の中の画像後ろの本文・段の中2枚 — いずれも `warnings` に一切出ない（実測） |
| リントの型 | `Diagnostic`（`types.ts:13-23`）には**混ぜず**、原稿オフセットを持つ独自型 | `Diagnostic` は変換器の警告の型。「原稿内の位置」は変換器が知らない情報 |
| docx で何を意味させるか | **横並びは作らない。幅%へコンパイルする** | `::: columns` すら無視して上下に流れる（実測）。劣化させて宣言する |
| docx の縦長画像 | **既定で直す**（高さ上限から逆算した width を Lua で注入） | 既定サイズは 72dpi 換算で幅は本文幅 5.83in で頭打ちだが**高さは頭打ちしない** — 400×800 が 5.56in×**11.11in** ＝ 1ページ超（実測）。`--dpi` は効かない |
| 既定プリセットの名前 | **`fitPage`（形式ごとの破綻だけ直す）**。素通しの `asIs` は比較用に別に残す | 「何も割り当てなければそのまま」と言いながら docx の高さを直すのは自己矛盾になる |
| 効かないノブを画面に出すか | **出さない** | 「動かしても何も起きない」を iPad の指の下に置かない |

## 2. 原稿に書くもの / 書かないもの

| 層 | 画像について持つもの |
|---|---|
| 内容（`.md`） | `![説明](name.png)` のみ。キャプション（alt）は内容なのでここ |
| テンプレート | レイアウトの枠（＝画像がどこにどれだけの大きさで収まるか） |
| 文書デザインデータ | どの画像にどの置き方を割り当てたか、指で動かした箱、文字の避け方、キャプションの扱い |

書かせないもの: `{width=}` `{height=}` / `{.full}` `{.aside}` / `{#im-xxxx}` の自動付与 /
`::: image-right` のような独自 fenced div / `::: columns` を配置手段として使うこと
（段の中で画像を扱うと無警告で消える組み合わせが2件ある。実測）。

「原稿を他のツールへ持ち出すと配置が消える」のは、装飾・文字サイズ・テンプレートで既に払っている代償と同じ。
**画像を素の `![](x.png)` のまま保てることのほうが、この製品では価値が高い。**

## 3. 形式ごとの意味

プリセットは6つ。**まずテンプレートで解けるものを見極め、後処理はその差分に限定する**（§9-2）。

| プリセット | pptx | docx | Web / epub |
|---|---|---|---|
| `fitPage`（既定） | pandoc の出力そのまま | 既定サイズ。**縦長は高さ上限で抑える** | 幅 100% |
| `bleed`（全面） | pic を `0,0,W,H` にし最背面へ | フルブリードは無い。幅 100% に縮退 | `width:100%; object-fit:cover` |
| `asideRight` / `asideLeft` | 枠を左右に振る（テンプレートで解ける可能性が高い） | 横並びは作らない。幅 45% で上下に流す | `float; width:45%` |
| `corner`（小さく右上） | 枠を縮めて右上へ、最前面 | 幅 25% ＋右寄せに縮退 | `float:right; width:22%` |
| `pair`（2枚並べる） | **`-implicit_figures` を採るなら不要**（正しく2枚に割れる）。採らないなら重なりをほどく | それぞれ幅 48% で上下に流す | `display:flex` |
| `asIs`（素通し） | 何もしない（比較・デバッグ用） | 同左 | 同左 |

### pptx — 後処理は例外のためだけ

pandoc は内容の形からレイアウトを勝手に選ぶ。既定テンプレート・16:9 の実測値:

| 原稿の形 | 出力 |
|---|---|
| 画像だけの段落 | `Title and Content`。`off 1181100,1193800 / ext 6781800×3390900` |
| `![説明](x.png)` | 同レイアウト。画像が縮み、キャプションが `ph idx="1"` の全幅 TextBox（`off 457200,4076700 / ext 8229600×508000`） |
| 本文・箇条書きと同居 | **`Content with Caption`**。左に本文（`ph idx="2" sz="half" type="body"`、slide 側の `<p:spPr />` は空）、右に画像 `off 3568700,1117600 / ext 5105400×2552700` |

**「本文＋画像でタイトルが左上に縮む」のは pandoc の歪みではない。**
slideLayout8 自身が `ph type="title"` に `off 457201,204787 / ext 3008313×871538` を持っており、
スライド側の明示 xfrm と**完全に同値**（実測）。xfrm を削っても継承先が同じなので何も変わらない。
全幅タイトルにしたければ削るのではなく**書く**（またはレイアウトを差し替える）。

後処理でやることは、テンプレートで解けなかったぶんだけ。**構造は変えない**
（要素の追加・削除・スライドの増減をしない）。

1. `<p:pic>` の `<a:off>` / `<a:ext>` を書き換える
2. 本文 sp の空の `<p:spPr />` に xfrm を注入する（`textSide`。**未検証** §9-4）
3. キャプション枠（`ph idx="1"`）の xfrm を画像に追従させる

実装上の罠（3段組プロトタイプで踏んだ）: pandoc は `<a:off x="…" y="…" />` と
**閉じ `/>` の前に空白を入れる**。置換の正規表現は `\s*\/>` にすること。

**重ね順に注意。** `applyDecorations`（`bridgeHtml.ts:771-775`）は `</p:grpSpPr>` の直後へ
**後から**挿すので、先に全面画像をそこへ移しても装飾の後ろに押し出される
（＝帯が写真の下に隠れる）。背面画像の移動は `applyDecorations` の**後**に行うか、
`SlideDecoration` に `z` を足すかを決めてから着手する。

### docx — 箱は無い。幅%へコンパイルする

`{width=}` `{height=}` は docx で**効く**（2in→1828800 EMU、30%→1600200。実測）ので後処理は不要。
デザインデータを Lua で AST の属性へ落とす。配線は `wireRuby`（`bridgeHtml.ts:1255`）と同型。

```lua
local seen = {}
function Image(el)
  local n = (seen[el.src] or 0); seen[el.src] = n + 1
  local w = RULE[el.src .. '#' .. n]
  if w then el.attributes.width = w end
  return el
end
```

**この経路の実利は縦長画像の既定修理**にある。400×800 の画像は既定で 1ページを突き抜ける。
高さ上限から逆算した `width` を注入すれば、**使い手が何もしなくても全部の縦長画像が直る**。
ページ寸法は reference.docx の `w:sectPr` から読む（引き継がれることは実測済み）。
reference-doc が無いときは本文幅 5.83in だけを使い、ページ高は推定しない
（`w:pgSz` が document.xml に無いことは実測）。

### Web / epub — 素直

同じ Lua 経路で `el.classes` に `morpho-bleed` 等を足し、CSS は `WEB_CSS` へ足す。
`embed-resources: true` は画像のある原稿に既に付く（`wireAssets`）ので自己完結 HTML になる。
**ただし HTML / epub の書き出し経路は存在しない**（`ExportFormat = 'pptx' | 'docx'`）ので、
当面はプレビューの中だけで終わる。

## 4. データモデル

```ts
/** 画像の同一性。アセット名 + 同名画像の文書内での出現順（0 始まり） */
export interface ImageAnchor { image: string; nth: number; }

export type ImagePreset = 'fitPage' | 'bleed' | 'asideRight' | 'asideLeft' | 'corner' | 'pair' | 'asIs';

export interface ImagePlacement {
  anchor: ImageAnchor;
  preset: ImagePreset;
  /** 指で動かしたときだけ入る。スライド寸法に対する比（0..1） */
  box?: { x: number; y: number; w: number; h: number };
  fit?: 'contain' | 'cover';
  textSide?: 'left' | 'right' | 'none';
  caption?: 'below' | 'overlay' | 'hidden';
  z?: 'back' | 'front';
}

// ConvertOptions へ1つ追加
images?: ImagePlacement[];
```

- `SlideImage`（`types.ts:94-100`）に `z?: 'back' | 'front'` を足す（プレビューの重ね順を実出力と揃えるため）
- `srcRect` / `crop` のような OOXML 語彙は境界に出さない。**`fit` が語彙で、実現方法はブリッジの内側**
- **箱は EMU ではなく比で持つ。** プレースホルダ枠はスライド寸法に追従しないので、
  比で持てば 4:3 テンプレートへ替えても図が中央に来る
- **参照数（`imageRefCounts`）は境界に足さない。** ブリッジは `doConvert` で原稿そのものを
  受け取っており（`wireAssets` は既に `md` を見ている）、参照数は内側で数えられる。
  境界に「原稿の統計」を足すと二重の真実になる

### `.morphodesign` — **version は 1 のまま**

`parseDesignFile` は `o.version !== 1` で**ファイル全体を null にする**。
2 に上げると旧版で装飾もグループも文字サイズも失われる。
`groups` を足したときも版を上げずに任意フィールドにした前例がある（`designs.ts:60-61`）。
`DesignData.version` は `1` のリテラル型なので、上げるなら型の変更も要る — **上げない。**

直す場所は**書き出しと読み込みの両方**（`serializeDesign` の spread、
`parseDesignFile` の sanitize、`loadDesign` の sanitize）。片方だけだと往復で消える。

### 原稿側の参照を数える純関数（`text/assetNames.ts`）

現行の `referencedImages` は `new Set` で重複を除去して返すので、アンカー解決にも総量検査にも使えない。

```ts
export interface ImageRef { name: string; nth: number; start: number; end: number; }
/** 原稿内の `![...](name)` を出現順に。start/end は body 内のオフセット */
export function imageRefs(source: string): ImageRef[];
```

**コードフェンスの中は数えない。** 既存の `referencedImages` も同じ穴を持つので同時に直す
（Markdown の書き方を説明する原稿で誤発火する）。
既存関数を派生にするときは、現行の除外規則を落とさないこと。

### 画像の原寸

`SlideImage.w/h` は「pandoc が決めた箱」であって原画の比ではない。
配置を当てた後はなおさら（`applyImagePlan` は `parsePics` より前に走る）。
実測でも tall(400×800) 単独は `ext 1701800×3390900` で、真の比 0.5 に対し 0.50187（pt 丸め）。
**取り込み時に原画の幅高を保存庫のメタとして記録する**（`saveAsset` の戻りに寸法を足す）。

## 5. UI

### 5.1 先に直す前提

`SlideSurface.tsx:194-221` は 装飾 → **画像** → 図形 の順に描いており、実出力の spTree
（`sp → sp → pic` ＝画像が最前面）と**逆**。今は pandoc が画像を本文枠の外に置くので
誰も気づかないが、`bleed` や `corner` を作った瞬間に露見する。
`z:'back' の画像 → 装飾 → 図形 → z:'front' の画像` に直す。**画像を触れるようにする前に。**

### 5.2 入口は2つだけ

| 入口 | 場所 | 挙動 |
|---|---|---|
| 「画像」ボタン | `EditorScreen.tsx:1520-1521` → `handleInsertImage`（`:475-508`） | ファイル選択の直後に配置シートを出す |
| プレビューの画像タップ | `SlideSurface.tsx:197-210` の `<Image>` を `Pressable` で包む | 同じシートを開く |

**挿入位置を変えるときは必ず空行で挟む。** 現行は改行を最大1つしか足さない（`:497-500`）ので、
「区間末尾へ挿す」だけにすると `![](a.png)\n# 二枚目` を作ってしまい、
実測で**2枚目のタイトルが消えて本文に `# 二枚目` という文字列が出る**。
しかも枚数は一致するので `contentIndexOf` は素通りする。
**「無警告のデータロスを見せる版」が無警告のデータロスを新設しかねない。**

### 5.3 `ImageSheet.tsx`（`DecorSheet` の兄弟）

装飾パネルには入れない（装飾は自分で足した図形、画像は原稿にあるもの）。
置き方カード / 文字の避け方 / キャプション / 収め方 / 微調整 / 一括適用。
各カードの下に**常時表示**（警告ではない）:「書籍では上下に並びます」など。

### 5.4 直接操作 — `ImageEditLayer.tsx`

`DecorEditLayer.tsx` が丸ごと雛形になる。写すべき知見: `PanResponder` +
`onPanResponderTerminationRequest: () => false`（`:178`）、確定は指を離したときだけ、
リサイズハンドルは**レイヤー直下の最後の兄弟**（`:222-233`）、当たり判定は `PAD_REACH=18`。

画像固有の差分は2点。**リサイズは縦横比固定が既定**（比は保存庫のメタから取る。§4）と、
**本文枠の端・スライド中央・セーフマージンへの吸着**。
**パネルを開いている間だけ**有効にする（常時可能にすると縦スクロール・段落長押し・
スライド選択タップと四つ巴になる）。

### 5.5 詰みを作らない

`bleed`（`z:'back'`）にした画像は本文の下に潜り、タップでは二度と選べなくなる。
シート上部に「このスライドの画像」一覧を必ず置く。

## 6. リント

`preview/imageLint.ts` に純関数1ファイル。**規則は `Converter.quirks`（`columns.md` §4）で
有効化し、自前 writer に差し替えたら黙る。**

| # | 重要度 | 何を捕まえるか |
|---|---|---|
| L1 | loss | 文中のインライン画像 —「スライドではこの画像が消えます（警告は出ません）」 |
| L2 | loss | 箇条書きの項目の中の画像 —「消えます。リストの外へ出してください」 |
| L3 | loss | 同じ段落に画像2枚 —「片方だけが残ります。空行で分けてください」 |
| L4 | loss | 段の中で画像の後ろに本文 —「この本文が消えます。段の中は『本文 → 画像』の順に」 |
| L5 | loss | 段の中に画像2枚 —「2枚目が消えます」 |
| L6 | layout | 画像の後ろに本文（段の外）—「タイトルの無いスライドに分かれます。**この原稿ではプレビューからのノート編集・改行編集・装飾編集が使えなくなります**」 |
| L7 | layout | **画像の直後に空行なしで見出し／水平線** —「見出しが本文の文字になります」（実測。枚数は一致するので既存の安全弁は素通りする） |
| L8 | loss | **総量検査**: `imageRefs(body)` の名前ごとの件数 ≠ 出力の `descr` 件数 |
| L9 | layout | 迷子の配置（anchor の画像が原稿から消えた）＋ 破棄 / 付け替え |

L8 は後処理の安全弁そのものでもある — **枚数が合わない名前には後処理を一切当てない**
（`applyDecorations` の `if (!zip[name]) return;` と同じ作法。ずれたら黙って pandoc 既定に戻る）。
L8 と L9 は writer 非依存なので、quirks が空でも残る。

**コードフェンスの中は見ない**（§4 と同じ理由）。
出し方は `useMemo(() => lintImages(body), [body])` で、`ConvertResult.diagnostics` には混ぜない。
**pandoc の警告に一切依存しないので 47ms すら待たない。** L8 だけは変換後に出る。

L1・L2・L3 は原稿の書き換えを1タップで出す。**内容の並べ替えを伴う L4 と L6 は必ず確認を挟み**、
書き戻し直前に対象区間の文字列一致を検証する（`handleApplyBreaks` の作法）。

前提として、`warnText` の `pretty` 化・`BlockNotRendered` の規則追加・
**`LoadedResource` を診断から外すこと**を先に済ませる（`columns.md` §6）。

## 7. プレビューとの一致

### 純関数を2箇所で書き直さない

```
planDeckImages(slideXmls, deck, layoutPhOf, placements) -> Plan[]   // 純関数・EMU
applyImagePlan(slideXml, plan) -> slideXml'                          // 文字列 → 文字列
```

どちらも `bridgeHtml.ts` に置き `window.__morpho…` で公開する（`check-scene.mjs` が vm から叩ける）。

**プレビュー側の挿入位置に注意がいる。** `parsePptx` の `slides.map` は
`decode → parseShapes → 継承解決 → parsePics` の順に走るので、
plan は**読む前**に当てる:

```
var xml = dec.decode(zip[n]);
xml = applyImagePlan(xml, plan[i]);      // ← ここ
var shapes = parseShapes(xml);
```

書き出し側は `doExport` で当てる。**実装は1つしかないので、原理的に食い違わない。**
（`textSizes.ts` の `adjustDeck` は `toExportSizes` を呼んでいて二重実装ではない —
繰り返してはいけないのは装飾のほう。装飾はプレビュー変換で後処理を通らず、
UI 側で別に再現している）

`fit:'cover'` だけは別で、`SlideSurface.tsx:207` が `resizeMode="stretch"` 固定のため
**実出力はトリミング・プレビューは引き伸ばし**になる。`SlideImage` に切り抜き矩形を持たせて
プレビュー側も描くか、`cover` を後の版へ送る。

### 先に直す既存の不具合

`findInherited` の照合順（`columns.md` §7 の A と C）。plan はこの継承解決の上に箱を組み立てるので、
**直さないまま画像配置を載せると誤った枠を基準に計算する。**

### カーソル同期への影響

**なし。** 後処理は座標だけを触り、スライドの枚数も順序も変えない。
`cursorSlide.ts` の境界規則には**規則を足さない** — 足せば pandoc の分割規則の再実装が始まる。
既存のずれ（「画像 → 本文」で割れる）は配置機能が作った問題ではないが、画像を使う人は確実に踏む。
事後の Alert を、L6 の事前の指摘で置き換える。

### 検査

`check-image-plan.mjs` を `npm run check` へ追加し、
`planDeckImages → applyImagePlan → parsePptx` を通して
「解析結果の `images[]` が plan と EMU 単位で一致」「`@ooxml-tools/validate` がエラー0」
「枚数が食い違う名前には一切触らない」を assert する。
あわせて `check-deck.mjs` に `SlideOutline.layout` の assert を1件足す（現在ゼロ）。

### 今回の設計中に測って決着したこと

- **画像はプレースホルダ枠に追従する**（§0）。「テンプレートで動かせない」は誤り
- **layout2 は座標を持たない**（マスターが持つ）。書き換えの空振りを結論と取り違えない
- **Content with Caption の小さい左上タイトルはレイアウト自身の設計**（スライド側の明示 xfrm と同値）
- **`-implicit_figures` で、キャプション付き2枚が正しく2枚に割れる**（キャプションも両方残る）
- **`![ ](x.png)`（空白1文字の alt）ではキャプション枠は出ない**
- **キャプション2枚のときの spTree 順は pic1 → cap1 → pic2 → cap2、キャプション枠は `ph idx="1"` が2つ**
- **`![](a.png)` の直後に空行なしで `# 見出し` を書くと、見出しが本文の文字になる**（枚数は一致する）
- 段の中の画像は**列枠に追従する**（`columns.md` §3）

## 付記: この設計が引き受けているコスト

- **原稿の可搬性のうち「配置」は落ちる。** 装飾・文字サイズで既に払っている代償だが、
  画像は「内容の一部」だと感じられやすいぶん抵抗は強い。
  既定を素通しに近く保ち、**触らなければ何も起きない**ことでしか和らげられない
- **pandoc が消したものは後処理では取り戻せない。** インライン画像・箇条書き内・同段落2枚目は
  出力に到達しないので触る対象が無い。だからリントは必須で、v0.14.0 が先に来る
- **`SlideDecoration` に `z` が無い。** 装飾は常に最背面なので、
  「全面写真の上に帯」は重ね順の決着（§3）とセットでしか成立しない
